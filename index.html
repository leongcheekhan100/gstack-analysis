1 Quick refresher: what are "skills" in Claude Code?

You already use skills — your WhatsApp skill and your superpowers plugin are skills. But let's make sure we're on the same page about how they work under the hood.

A skill is like a cheat sheet you hand to Claude before asking it to do something. When you type /whatsapp, Claude reads your ~/.claude/skills/whatsapp/SKILL.md file and suddenly "knows" how to send WhatsApp messages. Without that file, it has no idea.

The SKILL.md file IS the skill. It's just a markdown file with instructions that gets loaded into Claude's memory (context window) when you invoke it.
Key concepts you need
Context window = Claude's working memory for this conversation. Everything loaded into it costs tokens (like credits). Bigger files = more tokens burned = less room for your actual conversation.

SKILL.md = The instruction file Claude reads when you invoke a skill. Lives inside a folder.

CLAUDE.md = Project-level instructions Claude always reads when you open a project (like your KKW or French Learning CLAUDE.md files).

Progressive disclosure = Instead of loading ALL instructions upfront, you give Claude a short summary and let it read more details only when needed. Like giving someone a table of contents first, not the whole book.

What Garry did right
  • Each skill gets its own folder — /ship, /review, /qa each have their own SKILL.md. That's modular and clean.
  • Auto-generated docs — SKILL.md files are generated from templates (.tmpl files), so they stay in sync with the code. Like auto-generating your KKW reports from data.
  • 3-tier testing — Free tests, AI-judge tests ($0.15), and full end-to-end tests ($3.85). This is serious engineering.
What Garry got wrong

The root SKILL.md (the main one) is 443 lines long. Every time Claude invokes /gstack, ALL 443 lines get loaded into memory. Here's what's inside:

Imagine every time you ask your KKW automation to generate ONE report, it first loads the entire manual for ALL 59 scripts into memory — including scripts for Binance screening, WhatsApp messaging, and French learning. That's the waste here. You'd want it to only load the report-generation instructions.

Skills folder — Skill A, B (basic and advanced), C

6 doob's proposed architecture

doob suggests separating skills (the knowledge/instructions) from agents (the workers who use those skills). Different agents can mix-and-match skills.

doob's ideal structure
project/
  skills/ ← just the instruction files, small and focused
    skill-a/
      SKILL.md ← short entry point (like a table of contents)
      references/ ← detailed docs, loaded only when needed
    skill-b/ ← another focused skill
    skill-c/
  agents/ ← workers that combine multiple skills
    agent-1/ ← "Side Worker" uses skill A + B
    agent-2/ ← "Manager" uses skill C + B (deeper)
Think of it like your insurance team:

Skills = training manuals (one for "prospecting", one for "claims", one for "commission calculation")
Agents = team members who use different combinations of those manuals

A new agent might only need the "prospecting" manual. A team leader needs "prospecting" + "commission calculation". You wouldn't hand everyone ALL the manuals on day one — you'd give them what they need for their role.

7 The verdict: who's right?

Where doob is RIGHT

  • Root SKILL.md is too fat — 443 lines / 16KB loaded every single time. The 220-line browser command reference should be a separate file that Claude reads only when it needs to browse.
  • Progressive disclosure saves tokens — Small index first, load details on demand. This is genuinely better. Your superpowers plugin already does this.
  • Skills should be modular — The idea that different agents can pick and choose which skills to use is solid architecture for complex setups.

Where doob is WRONG or exaggerating

  • "Wrong folder structure" — Actually wrong. The repo HAS 12 separate skill folders, each with its own SKILL.md. doob either didn't look at the repo properly, or ignored this.
  • "Many bad practices" — Vague and unsupported. The repo has auto-generated docs, a 3-tier test suite, and a proper build pipeline. That's better than 95% of Claude Code setups out there.
  • "Clubs all knowledge in one file" — Factually wrong. There are 11+ separate SKILL.md files. The problem is ONLY the root one being too large, not that "everything is in one file".
  • Dismissive tone — "Bad practices junior engineers shouldn't adopt" is harsh for a working, battle-tested 19k-star repo from a YC CEO who clearly uses it daily.

Bottom line

doob spots a real issue — the root SKILL.md is too large and wastes tokens by loading everything upfront. His progressive disclosure recommendation is solid and worth applying.

But he oversells the criticism by calling the whole repo "bad practices" without acknowledging that the sub-skills ARE already modular (12 separate folders), and the engineering quality (auto-generated docs, 3-tier testing) is genuinely strong. He also claims everything is "in one skill.md file" which is factually wrong — he probably only looked at the root file and assumed that was it.

It reads like someone who learned one good pattern and now applies it as the universal standard, without fully examining what the repo actually contains.

doob's accuracy: ~40% right, ~60% overstated or wrong
